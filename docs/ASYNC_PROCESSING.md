# Асинхронная и параллельная обработка файлов

## ✅ Текущее состояние

**Асинхронный режим полностью реализован и готов к использованию!**

### Как это работает:

1. **По умолчанию** (`ASYNC_MODE=true` в `.env` файле):
   - Используется `AsyncMessageBus`, который отправляет сообщения в Redis очередь
   - Все команды и события маршрутизируются в `async` transport
   - Сообщения попадают в очередь Redis и ждут обработки worker'ами

2. **Синхронный режим** (`ASYNC_MODE=false`):
   - Используется `SynchronousMessageBus` для немедленной обработки
   - Все файлы обрабатываются последовательно, один за другим
   - Подходит для небольших объемов данных (до нескольких тысяч файлов)

### Инфраструктура:

- ✅ `AsyncMessageBus` - отправляет сообщения в Redis очередь
- ✅ `ConsumeMessagesCommand` - команда для потребления сообщений из очереди
- ✅ Redis транспорт настроен и работает
- ✅ RabbitMQ транспорт доступен (опционально)
- ✅ Worker сервис в Docker Compose
- ✅ Все команды и события маршрутизируются в `async` transport

## 📊 Производительность

**Синхронный режим** (`ASYNC_MODE=false`):
- ~10-50 файлов/сек (зависит от размера файлов)
- Для 2 ТБ (~10,000 файлов): ~3-17 минут
- Один поток обработки

**Асинхронный режим** (`ASYNC_MODE=true`):
- **1 worker**: ~10-50 файлов/сек (как синхронный режим)
- **4 worker'а**: ~40-200 файлов/сек (4× быстрее)
- **8 worker'ов**: ~80-400 файлов/сек (8× быстрее)
- **Для 2 ТБ (~10,000 файлов)**: ~25 секунд - 2 минуты (с 8 worker'ами)

## 🚀 Как это работает

### Архитектура

1. **Сканирование**: `ScanFilesCommand` сканирует директорию и отправляет события `FileDiscovered` в очередь (Redis/RabbitMQ)
2. **Очередь**: Сообщения попадают в очередь `async` transport
3. **Workers**: Один или несколько worker'ов обрабатывают сообщения из очереди параллельно
4. **Pipeline**: 
   - `FileDiscovered` → `IngestFileCommand` → извлечение метаданных, расчет хэша
   - `FileProcessed` → `OrganizeFileCommand` → копирование файла с сохранением метаданных
   - `FileOrganized` → логирование успешной обработки

### Преимущества асинхронного режима

- ✅ **Параллельная обработка**: Несколько файлов обрабатываются одновременно
- ✅ **Масштабируемость**: Можно запустить несколько worker'ов для увеличения скорости
- ✅ **Отказоустойчивость**: Автоматические повторы при ошибках
- ✅ **Мониторинг**: Просмотр очереди и статистики обработки
- ✅ **Производительность**: Для больших объемов данных обработка в разы быстрее

### Как запускается

#### Вариант 1: Использование Docker Compose Worker

```bash
# 1. Запустить приложение с worker'ом
make up-worker

# 2. В другом терминале запустить сканирование
make run

# Worker автоматически обработает все сообщения из очереди
```

#### Вариант 2: Ручной запуск worker'а

```bash
# 1. Запустить приложение
make up

# 2. Запустить сканирование (сообщения попадут в очередь)
make run

# 3. В другом терминале запустить worker
make consume

# Или запустить несколько worker'ов для параллельной обработки:
make consume-workers WORKERS=8
```

### Настройка параллелизма

#### Количество worker'ов

Количество параллельно обрабатываемых файлов = количество worker'ов

**Рекомендации:**
- **CPU-bound задачи** (извлечение метаданных, расчет хэша): количество worker'ов = количество CPU ядер
- **I/O-bound задачи** (копирование файлов): количество worker'ов = 2-4 × количество CPU ядер
- **Для 2 ТБ данных**: рекомендуется 4-8 worker'ов

## 📝 Настройка

Асинхронный режим настраивается через переменную окружения `ASYNC_MODE` в файле `.env`:

```bash
# В .env файле:
ASYNC_MODE=true   # Включить асинхронный режим (по умолчанию в .env.example)
ASYNC_MODE=false  # Отключить асинхронный режим (синхронная обработка)
```

**По умолчанию** в `.env.example` установлено `ASYNC_MODE=true`. Если переменная не установлена в `.env`, используется значение `false` (синхронный режим).

Для переопределения при запуске:
```bash
ASYNC_MODE=false make run
```

## 🔒 Защита от дубликатов и race conditions

### Идемпотентность обработки

Приложение защищено от повторной обработки файлов даже при параллельной работе нескольких worker'ов:

1. **Проверка перед обработкой**: Перед обработкой файла проверяется, был ли он уже обработан (по пути, размеру и хэшу)
2. **Атомарная вставка в БД**: Используется `INSERT OR IGNORE` для предотвращения race conditions между worker'ами
3. **UNIQUE constraint**: В базе данных есть уникальный индекс на `(file_path, file_size, file_hash)`, который предотвращает дубликаты на уровне БД

### Как это работает

#### В синхронном режиме:
- Файл проверяется перед обработкой через `isProcessed()`
- Если файл уже обработан, он пропускается

#### В асинхронном режиме:
- Файл проверяется перед обработкой через `isProcessed()`
- **Дополнительно**: При сохранении в БД используется `INSERT OR IGNORE`, что гарантирует атомарность операции
- Если несколько worker'ов одновременно пытаются обработать один и тот же файл:
  - Первый worker успешно сохраняет запись
  - Остальные worker'ы получают `0 affected rows` и обновляют существующую запись (без ошибок)

### Дедупликация по хэшу

Приложение также предотвращает копирование файлов с одинаковым содержимым (разные пути, одинаковый хэш):

- Если файл с таким же хэшем уже существует в базе данных, новый файл пропускается
- В логах будет сообщение: `Duplicate file detected (same hash, different path), skipping ingestion`

### Логирование

В асинхронном режиме важные события логируются на уровне `INFO` (вместо `DEBUG`), чтобы их было видно в консоли:

- ✅ `File already processed, skipping` - файл уже был обработан ранее
- ✅ `Duplicate file detected, skipping ingestion` - найден дубликат (тот же хэш, другой путь)
- ✅ `File ingested successfully` - файл успешно обработан
- ✅ `File organized successfully` - файл успешно перемещен

Все логи также сохраняются в файл `var/log/*.log` с уровнем `DEBUG` для детального анализа.

### Повторный запуск

Если вы запустите команду сканирования повторно:

1. **Файлы уже обработанные** будут пропущены (проверка по пути, размеру и хэшу)
2. **Новые файлы** будут обработаны
3. **Дубликаты** (файлы с тем же хэшем, но другим путем) будут пропущены

Это означает, что можно безопасно запускать команду несколько раз - она не будет обрабатывать файлы повторно.
